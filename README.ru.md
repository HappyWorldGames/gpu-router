# gpu-router

[English](README.md) | **Русский**

Прокси-очередь для одной общей видеокарты (или APU с общей памятью), на которой
живут сразу **ComfyUI** и **llama.cpp** (`llama-server` в router-режиме). Он по
очереди передаёт GPU то одному, то другому сервису, выгружает модели того, кто
уступает, и показывает на веб-странице, кто сейчас занимает GPU.

Один бинарник на Go, без зависимостей кроме двух библиотек.

## Зачем это нужно

Если ComfyUI и llama.cpp держат модели в одной и той же видеопамяти (особенно
на APU вроде Radeon 780M, где «VRAM» и ОЗУ это одно и то же), одновременная
работа приводит к OOM, зависаниям и выбиванию процессов ядром. Клиенты вроде
Open WebUI или n8n ничего об этом не знают и шлют запросы когда им вздумается.

gpu-router стоит между клиентами и сервисами и решает это:

- запросы к GPU выстраиваются в **очередь** (FIFO), а не идут одновременно;
- перед передачей GPU другому сервису прежний **выгружает** модели (мягко, через
  API), а если не отпускает память, **выбивает** его процессы;
- следит за **оперативной памятью** и не даёт системе дойти до OOM-killer'а ядра;
- рисует **страницу состояния**: занятость GPU, статус сервисов, скорость
  генерации в токенах в секунду.

## Возможности

- **Очередь запросов** к ComfyUI (`/prompt`) и llama.cpp (любой POST, который
  может запустить генерацию). Служебные пути (`/props`, `/models`, `/tokenize`, `
  /slots` и т. п.) идут напрямую, минуя очередь.
- **Передача GPU:** ComfyUI освобождается через `/interrupt` \+ `/free`, llama
  через `/models/unload`. Если после `release_timeout` память не освободилась,
  процессы юнита получают `SIGKILL`.
- **Учёт VRAM по процессам:** из `fdinfo` ядра (AMD, Intel, без внешних утилит)
  или через `nvidia-smi`. Процессы сервисов находятся по их systemd-юнитам.
- **Параллельные запросы к llama.cpp:** количество слотов (`parallel`) берётся
  из вашего `models.ini`. Подробнее ниже.
- **Защита памяти:** предупреждения, ожидание освобождения ОЗУ перед задачей,
  аварийная остановка при критически малой памяти. Если GPU простаивает, модель
  так просто не выбивается.
- **Таймауты, учитывающие очередь:** зависший запрос обрывается, только если за
  ним реально кто-то ждёт.
- **Выгрузка по простою** для ComfyUI (настраивается).
- **Страница состояния** для главной страницы домашнего сервера: кто держит GPU,
  сколько запросов идёт, память, токены в секунду, доступность сервисов.

## Как это устроено

```
 Open WebUI, n8n, ...                      браузер
        │                                     │
        ▼                                     ▼
  :8080  llama-прокси                  :8188  ComfyUI-прокси
        └──────────── gpu-router ─────────────┘
              очередь · учёт VRAM · выгрузка · watchdog
        │                                     │
        ▼                                     ▼
  :8180  llama-server (router)         :8288  ComfyUI

  :8190  /api/status  → страница состояния (через Caddy или напрямую)
```
Клиенты переключаются на порты прокси (`8080` и `8188`), а сами сервисы
переезжают на другие порты (`8180` и `8288`).

Порядок обработки одной задачи:

1.  Задача встаёт в очередь (`queue.max_size`, ожидание ограничено `
    queue.wait_timeout`).
2.  Когда подходит очередь, прокси готовит GPU: ждёт, пока ComfyUI закончит
    текущую генерацию, выгружает модели конкурента, проверяет, что память
    действительно освободилась (с учётом `residual_mb`), и ждёт нужный запас ОЗУ
    (`gpu.min_available_mb`).
3.  Запрос проксируется на бэкенд. Для llama ответ пересылается потоком, для
    ComfyUI прокси дожидается окончания генерации.
4.  Watchdog раз в `gpu.watchdog_interval` секунд проверяет, не держат ли оба
    сервиса память одновременно (например, кто-то обратился к бэкенду
    напрямую), и выбивает «лишнего».

## Требования

- Linux с systemd (процессы сервисов определяются по их cgroup).
- Go 1.21+ для сборки.
- ComfyUI и llama.cpp (`llama-server` в router-режиме с `models.ini`),
  запущенные как systemd-юниты.
- Права читать `/proc/\<pid>/fdinfo` процессов сервисов и посылать им сигналы:
  запускайте от root или от того же пользователя, что и сервисы.
- Источник данных о VRAM: AMD/Intel работают через `fdinfo` (основное
  тестирование: AMD Radeon 780M, APU). Для NVIDIA есть режим `nvidia-smi`, но на
  своей карте проверьте его отдельно.

## Быстрый старт

### 1\. Сборка

```bash
go mod tidy
go build -o gpu-router .
```
### 2\. Перенесите сервисы на другие порты

Прокси занимает привычные порты, поэтому сами сервисы должны слушать другие.
Например, в юнитах: ComfyUI на `8288`, llama-server на `8180`. Эти значения
указываются в `comfyui.port` и `llama.port`.

### 3\. Конфиг

```bash
cp config.example.yaml config.yaml
```
Обязательно проверьте:

- `comfyui.unit` и `llama.unit`: имена ваших systemd-юнитов (`systemctl
  list-units | grep -i comfy`);
- порты бэкендов и порты прокси;
- `proxy.listen_host`: по умолчанию слушает все интерфейсы, а **собственной
  авторизации у прокси нет**, поэтому закройте порты `8080`/`8188` файрволом от
  внешней сети;
- `comfyui.residual_mb` и `llama.residual_mb`: сколько памяти сервис вправе
  держать после выгрузки. Подберите по строке `остаток N МБ` в логе.

Все параметры описаны комментариями в `config.example.yaml`.

### 4\. Запуск

```bash
./gpu-router config.yaml
```
Для постоянной работы возьмите юнит из `deploy/gpu-router.service`:

```bash
sudo install -D gpu-router /opt/gpu-router/gpu-router
sudo install -m 600 config.yaml /opt/gpu-router/config.yaml
sudo cp deploy/gpu-router.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now gpu-router
```
### 5\. Направьте клиентов на прокси

Open WebUI, n8n и всё остальное должны ходить на `:8080` (llama) и `:8188`
(ComfyUI), а не напрямую на сервисы. Прямые обращения к бэкендам обходят
очередь; watchdog их заметит и разрешит конфликт, но надёжнее такого не
допускать.

## Параллельные запросы к llama.cpp

По умолчанию llama получает по одному запросу. Если в `models.ini` у модели
указан `parallel` больше 1, прокси пускает к уже загруженной модели столько
запросов одновременно, сколько там слотов.

```yaml
llama:
  models_ini: "/путь/к/models.ini"
```
Правила:

- Запрос присоединяется к идущим, только если обращается к той же модели (поле 
  `model` в теле) и есть свободный слот. Иначе он ждёт.
- Запрос к другой модели и любая задача ComfyUI ждут, пока завершатся все
  идущие запросы llama. Порядок очереди сохраняется, поэтому ComfyUI не
  «голодает».
- Значение `parallel` берётся из секции модели, а если его нет, то из `[*]`.
  Распознаются ключи `parallel`, `np`, `n-parallel`. Недопустимые значения и `\-1`
  (авто) считаются за 1.
- Файл читается один раз при запуске прокси. После правки `models.ini`
  перезапускайте llama.cpp и gpu-router вместе: сам llama.cpp применяет `parallel`
  только при (пере)запуске.

Заметьте, что без `kv-unified` контекст `ctx-size` делится между слотами, то
есть у каждого запроса он будет меньше. Проверьте `total_slots` и размер
контекста слота в `/props` вашей сборки.

## Защита от нехватки памяти и таймауты


|Параметр|Что делает|
|-|-|
|`gpu.min_available_mb`, `gpu.mem_wait`|Перед задачей ждёт, пока свободная ОЗУ вырастет выше порога (до `mem_wait` секунд), потом идёт на свой риск. В логе список самых тяжёлых процессов.|
|`gpu.critical_available_mb`|Если свободной ОЗУ меньше порога два замера подряд, прокси останавливает того, кто держит GPU: сначала мягко, через ~4 с без улучшения `SIGKILL` юнита. Быстрее и точечнее OOM-killer'а ядра.|
|`gpu.critical_idle_available_mb`|То же, но когда задачи нет и очередь пуста. Модель не выбивается, пока память не упадёт ниже этого порога (по умолчанию половина критического; `\-1` = при простое не выбивать никогда).|
|`gpu.kill_on_leak`|`false` = только логировать, не убивать.|
|`queue.task_timeout`|Потолок на одну задачу. Срабатывает только если за ней кто-то ждёт.|
|`queue.exec_idle_timeout`|Нет данных от бэкенда столько секунд: обрыв запроса. Тоже только если за ним кто-то ждёт. Для длинного контекста значение нужно ставить с запасом: обработка промпта на 90 тысяч токенов может молчать минутами.|
|`queue.comfy_idle_timeout`|Максимальное время генерации ComfyUI.|

## Панель состояния

Прокси поднимает отдельный маленький сервер (по умолчанию `127.0.0.1:8190`) с
одним адресом `/api/status`, который отдаёт JSON: кто держит GPU, длина очереди,
состояние ComfyUI и llama, память, скорость генерации, доступность сервисов. Он
не проходит через очередь и не пишет в лог, поэтому опрос страницы никому не
мешает.

Страницу `web/index.html` можно отдавать любым веб-сервером. Пример для Caddy
лежит в `deploy/Caddyfile`:

```caddy
home.home {
    handle /api/* {
        reverse_proxy 127.0.0.1:8190
    }
    handle {
        root * /usr/share/caddy   # сюда положите web/index.html
        file_server
    }
}
```
Страница опрашивает статус раз в 2 секунды, ничего не загружает с внешних
адресов, подстраивается под светлую и тёмную тему и переключается между русским
и английским (язык берётся из браузера, выбор запоминается). Список сервисов
задаётся в `dashboard.services` (доступность проверяется по TCP).

Скорость в токенах в секунду прокси считает, подглядывая в проходящий ответ
llama (ничего не меняя в нём): живая скорость по скользящему окну и итоговая из
поля `timings` последнего чанка. Если клиент просит сжатый ответ, цифры не
появятся, но на проксирование это не влияет.

|Адрес|Назначение|
|-|-|
|`:8188`, `:8080` `/status`|Отладочный статус прокси.|
|`127.0.0.1:8190` `/api/status`|JSON для страницы состояния.|

## Логи

Строки логов помечены тегами: `\[Start]`/`\[Done]` (задача
началась/закончилась), `\[Queue]`, `\[Release]`/`\[Unload]` (выгрузка), `\[Evict]`
(принудительное выбивание), `\[MemGuard]`/`\[Mem]` (память), `\[Worker]`
(таймауты), `\[Parallel]` (слоты). Если вашу модель что-то выгрузило, начните с:

```bash
journalctl -u gpu-router | grep -E "MemGuard|Evict|Release|Unload|Worker"
```
Параметры `logging.verbose`, `logging.requests` и `logging.mem_trace` управляют
подробностью.

## Ограничения

- Нет авторизации: защищайте порты файрволом.
- Работает на одной машине с сервисами (нужны `/proc` и systemd).
- Прямые обращения к бэкендам в обход прокси не учитываются очередью.
- Параллелятся только запросы к одной и той же модели llama.
- Оценка занятой памяти по процессам включает и VRAM, и GTT (общую память), как
  её видит ядро.

## Разработка

```bash
go test -race ./...
```
Тесты проверяют разбор `models.ini`, логику допуска параллельных запросов
(присоединение, ожидание слота, другая модель, ComfyUI, уход клиента), разбор
потока для счётчика токенов и таймауты, зависящие от очереди. Они не требуют ни
GPU, ни запущенных сервисов.
